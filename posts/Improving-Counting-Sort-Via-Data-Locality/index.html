Improving Counting Sort Via Data Locality

Created2026-04-18|Updated2026-04-19|Study Notes
|Post Views:

Overview

This semester our Algorithms project asked each group to take a research paper, implement the proposed algorithm from scratch in Java and replicate the paper’s benchmark experiments.

Our group was assigned Paper 2: “Improving Counting Sort Algorithm Via Data Locality”. The core claim is deceptively simple: Counting Sort runs 2-4x faster on sorted input than on random input - not because of any difference in time complexity (O(n + r) in both cases) - but purely because of CPU cache behaviour. The paper then proposes a hybrid sorting algorithm that exploits this observation to make Counting Sort fast on any input.

The Cache Miss Problem

Counting Sort maintains two auxiliary arrays: a count[] array of size r (the value range) and an output[] array
of size n. During the placement phase, each element arr[i] is written to output[count[arr[i]] - 1]. The index
into output[] is determined by the value of the element — not its position — so access patterns are
data-dependent.

  • Random input → values are scattered → count[] accesses jump around → many cache misses → slow
  • Sorted input → values increase monotonically → count[] accesses are sequential → cache-friendly → fast

Despite identical O(n + r) complexity, this hardware-level difference produces a dramatic real-world gap.

We compared the Classic Counting Sort on random input and sorted input with n = r:

n = r T1: Random (ms) T2: Sorted (ms) Speedup T1/T2
1,000,000 1.09 0.467 2.27×
2,000,000 2.84 0.910 3.57×
3,000,000 3.75 1.39 4.09×

The speedup grows with input size - larger arrays amplify the cache pressure. This was the key insight motivating to improve this situation.

The Proposed Algorithm

The algorithm has two phases:

Phase 1 - Modified QuickSort (Preprocessing)

Run a modified QuickSort that tracks the local min and max at each recursive call. Stop recursing into a sub-array once it satisfies the cache-friendliness condition:

(maxValue - minValue) + (high - low) <= C

where C = 1000 (the paper’s threshold). At this point, the sub-array is small enough and value-dense enough that its count[] array will fit in L1/L2 cache.

Phase 2 - Local Counting Sort

Apply Counting Sort independently to each leaf partition using only the local value range ([min, max]). This keeps count[] tiny and access patterns sequential — low cache misses guaranteed.

Here is the implementation of the core modifiedQuickSort method:

private static void modifiedQuickSort(int[] arr, int low, int high,
                                      int maxValue, int minValue) {
    if (low >= high) return;

    // Cache-friendliness condition — switch to Counting Sort
    if ((maxValue - minValue) + (high - low) <= C) {
        countingSortLocal(arr, low, high, minValue, maxValue);
        return;
    }

    int pivotIndex = partitionMedianOfThree(arr, low, high);
    int midValue = arr[pivotIndex];

    // Left partition: values ≤ pivot
    modifiedQuickSort(arr, low, pivotIndex - 1, midValue, minValue);
    // Right partition: values ≥ pivot
    modifiedQuickSort(arr, pivotIndex + 1, high, maxValue, midValue);
}

And the local Counting Sort applied to each partition:

private static void countingSortLocal(int[] arr, int low, int high, int min, int max) {
    int range = max - min + 1;   // local range — fits in cache
    int size  = high - low + 1;

    int[] count  = new int[range];
    int[] output = new int[size];

    for (int i = low; i <= high; i++) count[arr[i] - min]++;
    for (int i = 1; i < range; i++)   count[i] += count[i - 1];
    for (int i = high; i >= low; i--) output[--count[arr[i] - min]] = arr[i];

    System.arraycopy(output, 0, arr, low, size);
}

Complexity:

  • Preprocessing (Modified QuickSort): O(n log n) average
  • Counting Sort phase: O(n + r) total across all partitions
  • Overall: O(n log n + n + r) - dominated by QuickSort, but with dramatically better cache behaviour than naive Counting Sort when r >> n.

Results

Table 2 — Hybrid Sort vs Classic Counting Sort (r >> n)

When the value range is much larger than the element count (r = 1,000,000, n = 1,000–3,000), classic Counting Sort must initialise and scan a huge sparse count[] array — massively cache-inefficient. Our hybrid eliminates this:

n r Preprocessing (ms) Local CountingSort (ms) Hybrid Total Classic Counting Sort
1,000 1,000,000 0.086 0.192 0.278 0.866
2,000 1,000,000 0.174 0.203 0.377 0.774
3,000 1,000,000 0.217 0.237 0.454 0.886

Speedup: 2.8x -> 2.05x -> 1.95x

Table 3 - Hybrid Sort vs Comparison-Based Sorting Algorithms (n = r)

n = r QuickSort (ms) Quick+Insertion Sort (ms) Proposed Hybrid Sort (ms)
1,000,000 73.09 60.70 43.89
2,000,000 154.50 136.07 92.64

The Hybrid Sort is ~1.48x faster than QuickSort+InsertionSort and ~1.49x faster than plain QuickSort at 2M elements.

A larger cache means the “random” case of classic Counting Sort already benefits from more data fitting in cache — so both absolute times are lower and the speedup ratios are compressed compared to the paper. Despite this, the directional trends are identical: sorted beats random, hybrid beats classic, and hybrid scales best. The core thesis of the paper is validated.

Reflections

A few things that stood out from working on this project:

The threshold C matter. Setting C = 1000 (the paper’s value) gave us the closest results. Increasing C produces fewer QuickSort recursion but larger partitions that may overflow the cache; decreasing C increases preprocessing overhead. Adaptive threshold tuning based on detected cache size is an obvious and interesting future direction.

Benchmark Java is tricky. JVM warmup, JIT compilation, and garbage collection all add noise. We ran 3 warmup rounds then averaged 5 measured runs for each data point. Without warmup, the first run of any algorithm shows anomalously high times.

The insight is hardware-aware, not just algorithmic. This paper is a reminder that theoretical complexity tells only part of the story. Cache behaviour, memory access patterns, and hardware architecture are just as important in practice.
